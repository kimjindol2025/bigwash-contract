## 1. 한 문장 결정

BigWash를 범용 세차장 SaaS로 판매하지 않는다. 대한이엔지가 이미 장비를 판매·설치한 고객에게 **고장, A/S 누락, 점검 시기 누락을 줄이는 연간 장비관리 서비스**를 판매하고, BigWash는 그 서비스를 안정적으로 운영하는 내부 시스템이 된다.

## 2. 누가 당장 돈을 내는가

### 1차 구매자

- 최근 90일 안에 대한이엔지 장비를 구매·설치한 세차장 점주
- 보증기간 종료가 60일 이내로 다가온 기존 고객
- 장비가 여러 대이거나 A/S 이력이 반복되는 사업장
- 신규 세차장 창업 패키지를 상담·계약 중인 예비 점주

이 고객들은 이미 장비와 창업에 돈을 지출하고 있다. 완전히 새로운 소프트웨어 예산을 설득하는 대신, 기존 장비 거래에 `안심관리 1년`을 붙인다.

### 실제 사용자

- 대한이엔지 대표·관리자: 계약, 고객, 장비, 미수금, 전체 A/S 현황
- 현장 담당자: 방문 일정, 증상, 조치, 사용 부품, 사진, 완료 처리
- 세차장 점주: A/S 접수, 예정일 확인, 처리 이력, 다음 점검일 확인

### 지금은 고객이 아닌 대상

- 대한이엔지와 거래 관계가 없는 전국 모든 세차장
- 단순 무료 장비대장을 찾는 사용자
- 대형 프랜차이즈 본사와 다점포 통합 운영팀

첫 유료 사례가 나오기 전에는 이들을 위한 기능을 만들지 않는다.

## 3. 고객이 사는 결과

고객은 CRM이나 AI를 사지 않는다. 다음 결과를 산다.

> 장비가 멈췄을 때 누구에게 무엇을 요청했는지 사라지지 않고, 점검 시기를 놓쳐 큰 고장으로 번지는 일을 줄여드립니다.

대한이엔지가 얻는 결과:

- 전화·카카오톡에 흩어진 A/S 요청을 한곳에서 관리
- 접수 누락과 재문의 감소
- 설치 장비와 보증기간을 고객별로 즉시 확인
- 정기점검·소모품 교체 시점에 재매출 발생
- 계약금·잔금·수리비 미수금 확인 시간 단축

점주가 얻는 결과:

- A/S 접수 여부와 방문 일정을 직접 확인
- 장비별 수리·부품 교체 이력 보존
- 보증 적용 여부와 예상 비용을 사전에 확인
- 다음 점검일을 놓치지 않음

## 5. 상품 구성과 가격 가설

소프트웨어 사용료가 아니라 장비관리 서비스로 표시한다. 출장비와 부품비의 포함 범위는 실제 원가 확인 후 확정한다.

### 기본 등록 — 장비 구매 고객에게 1년 포함

- 설치 장비대장
- 보증기간 기록
- 모바일 A/S 접수 링크
- 처리 상태 확인
- 수리·부품 이력

목적은 별도 매출보다 신규 장비 계약의 신뢰와 이후 유료 전환 기반을 만드는 것이다.

### 안심관리 — 연 36만 원 가격 가설

- 기본 등록 전체
- 점검 시기 알림
- 분기별 장비 상태 확인 연락
- A/S 우선 일정 배정
- 연간 장비관리 보고서
- 현장 출장비·부품비 별도

### 안심관리 현장형 — 연 79만 원부터 가격 가설

- 안심관리 전체
- 연 2회 정기 현장점검
- 점검 체크리스트와 결과 보고
- 소모품 교체 권고
- 지역·거리별 출장 조건, 부품비 별도

### 첫 유료 검증상품 — 90일 9만 9천 원

- 기존 고객 한 곳의 장비 등록
- A/S 접수·상태 공유
- 점검 일정 1회 설정
- 90일 종료 후 연간 상품 전환 시 결제액 차감

첫 검증에서는 할인보다 `첫 세 곳만 직접 세팅`이라는 제한을 사용한다.

## 6. MVP 범위

> **2026-07-17 우선순위 갱신**: 1~5, 7번(A/S 축)은 Phase 1로 이미 구현·검증됨
> (`docs/04-washcare-api.md`). 활동비중(판매40·홍보20·서비스15·출장25) 기준으로는
> 서비스+출장(A/S)=40%가 이미 커버됐고, **판매(40%)의 관리 관점 보강과 홍보(20%,
> 9~10번, 완전 미구현)가 다음 우선순위**다.
>
> **2026-07-17 후속: 9, 10번 및 판매 관리 흐름 보강 구현 완료.** 아래 상태 표시 최신화.

### 반드시 구현

1. 고객과 사업장 — ✅ 구현됨 (Phase 1)
   - 점주명, 연락처, 사업장 주소, 담당자, 거래 상태
2. 설치 장비대장 — ✅ 구현됨 (Phase 1)
   - 장비 종류, 모델, 일련번호, 설치일, 보증 종료일, 계약 연결
3. A/S 접수 — ✅ 구현됨 (Phase 1)
   - 사업장, 장비, 증상, 긴급도, 사진, 접수 채널
4. A/S 상태 흐름 — ✅ 구현됨 (Phase 1)
   - `접수됨 → 일정 확정 → 방문/처리 중 → 완료`와 취소
5. 방문·수리 이력 — ✅ 구현됨 (Phase 1)
   - 담당자, 방문일, 원인, 조치, 사용 부품, 비용, 다음 점검일
6. 운영 대시보드 — 부분 구현(Admin UI 목록/상세 + 보증 임박 ✅). 미수금·지연건 집계는 미구현
   - 미배정 A/S, 오늘 방문, 지연 건, 점검 임박(✅ `/care/warranty-expiring`), 미수금
7. 고객용 모바일 상태 링크 — ✅ 구현됨 (Phase 1, 완료 후 7일 유지)
   - 로그인 없이 안전한 개별 링크로 현재 상태와 예정일 확인
8. 주간 운영 보고 — 미구현
   - 미처리 A/S, 다음 주 방문, 점검 대상, 미수금 요약
9. **부품판매 — ✅ 구현됨 (매출 30%, 2026-07-17)**
   - `PartSale` 등록(장비·A/S 연결 선택 가능), 매장/온라인 채널 구분. 결제 자체는 미연동
10. **휴면기 관리·홍보 — ✅ 구현됨 (활동 20%, 2026-07-17)**
   - `OutreachTouch` 생성·발송·반응 기록, 다음 접촉일 자동 산정, A/S·부품판매·
     신규판매로의 전환 추적(`converted_to`/`converted_ref_id`)
11. **판매 관리 흐름 — ✅ 구현됨 (활동 40%, 2026-07-17)**
    - `POST /care/sales`로 견적·계약 → 고객/사업장 → 장비 → 관리링크 발급 → 첫 접촉
      예약을 단일 트랜잭션으로 orchestrate. 6·9·10번이 요구하던 "판매(40%)의 관리
      관점 보강"이 이 항목으로 충족됨

### 1차 MVP에서 제외

- 네이티브 모바일 앱

```text
OutreachTouch (2026-07-17 추가 — 홍보/휴면기 관리, 지금까지 전혀 없었음)
  id, site_id, equipment_id (nullable), touch_type(안부·점검알림·교체제안·프로모션),
  channel(전화|카카오톡|문자|이메일), sent_at, response(무응답|긍정|부정|결과전환),
  next_touch_at, converted_to (nullable — ServiceTicket/PartSale/신규Equipment 중
  이 홍보로 실제 전환됐다면 어느 것인지)
```

`ServiceVisit`의 `parts` 필드는 A/S 방문 중 "사용"한 부품(비용 항목)이고, `PartSale`은
A/S와 무관하게 부품을 "판매"하는 별도 매출 이벤트다. 이 둘을 하나로 합치면 안 된다 —
전자는 A/S 원가, 후자는 독립 매출이다.

모든 외부 공유 링크에는 추측하기 어려운 별도 토큰을 사용하고 내부 순번 ID를 노출하지 않는다.

## 9. 핵심 업무 흐름

> **2026-07-17 갱신**: 장비 한 대의 A/S 주기는 ~3년이라 "A/S 처리"만으로는 시스템이
> 대부분의 기간 동안 할 일이 없다. 실제 상시 순환은 **판매 → (휴면기 동안 주기적 홍보)
> → [A/S 또는 부품판매 또는 교체판매] → 완료 → 휴면기 복귀**다. 아래 순서를 이 순환
> 기준으로 다시 정리했다 — "휴면기 관리"가 가장 자주 도는 흐름이고, A/S·부품판매·
> 교체판매는 그 결과로 드물게 발생하는 이벤트다.

### 신규 장비 판매 (사이클의 시작 = 재시작)

```text
견적·계약 (매장 85% / 온라인 15%)
→ 고객/사업장 생성
→ 설치 장비와 일련번호 등록
→ 보증 시작
→ 고객에게 장비관리 링크 전달
→ 첫 접촉 일정(OutreachTouch) 생성 → 휴면기 관리로 진입
```

### 휴면기 관리 (판매 이후 ~3년, 가장 자주 도는 흐름)

```text
OutreachTouch 대상 생성 (마지막 접촉일 기준 주기 도래)
→ 연락 (전화·카카오톡·문자·이메일)
→ 반응 기록: 무응답 / 긍정(점검·구매 의향) / 부정 / 즉시 전환
→ 전환되면 아래 셋 중 하나로 연결:
   - A/S 처리로 이동 (증상 있음)
   - 부품판매로 이동 (소모품 교체 시점)
   - 신규 장비 판매로 이동 (교체 제안 수락)
→ 전환 안 되면 next_touch_at 갱신 후 휴면기 유지
```

### A/S 처리 (드물게 발생, ~3년 주기)

```text
전화·카카오톡·고객 링크 접수 (또는 휴면기 관리에서 전환)
→ 운영자가 티켓 생성 또는 확인
→ 담당자와 방문일 배정
→ 고객에게 상태 링크 안내
→ 현장에서 원인·조치·부품(사용) 기록
→ 비용·보증 여부 확정
→ 완료 확인 → 휴면기 관리로 복귀 (다음 접촉 주기 갱신)
```

### 부품판매 (매출 30%, A/S와 독립적으로도 발생)

```text
휴면기 관리에서 전환 또는 매장·온라인 직접 문의
→ PartSale 생성 (equipment_id 있으면 연결, 없어도 판매 가능)
→ A/S 방문 중 판매라면 ticket_id 연결
→ 결제 (매장 즉시결제 중심, 10장 결제 원칙 재사용)
→ 완료 → 휴면기 관리로 복귀
```

## 10. 결제·정산 준비

### 출시 초기

첫 세 고객은 기존 대한이엔지 거래 방식대로 견적서·계좌이체·세금계산서를 사용한다. 결제 링크보다 실제 유료 수요 검증이 먼저다.

### 자동결제가 필요해지는 시점

- 유료 관리계약 10곳 이상
- 갱신 누락이 실제 문제로 발생
- 고객이 카드·정기결제를 반복 요청

국내 사업자 기준으로는 빠른 단일 PG 도입 시 토스페이먼츠, 여러 PG 비교·전환이 필요하면 포트원을 검토한다. 도입 전 사업자등록증, 통신판매업 신고, 홈페이지 사업자정보, 이용약관, 개인정보처리방침, 환불정책을 준비한다.

### 결제 전에 반드시 확정할 세 가지

1. **멱등키**: `care_plan_id + billing_period`를 주문의 유일키로 사용해 동일 기간 중복 결제를 막는다.
2. **웹훅 안전성**: 결제 이벤트 원문과 PG 이벤트 ID를 별도 저장하고, 같은 이벤트 재수신은 무시한다. `paid` 이후 늦게 온 `ready` 이벤트가 상태를 되돌리지 못하게 한다.
3. **부분 환불**: 관리기간 경과분, 이미 수행한 정기점검·출장, 사용 부품을 분리한다. 현장 서비스가 수행된 뒤에는 소프트웨어 기간만 단순 일할 환불하지 않는다.

## 11. 마케팅 시스템

### 1단계: 패턴 수집

최근 고객 통화·카카오톡·A/S 기록에서 고객 표현을 수집한다.

- “접수된 건가요?”
- “언제 방문 가능해요?”
- “이거 보증되는 건가요?”
- “지난번에 어떤 부품 갈았죠?”

홍보 문구는 AI 용어가 아니라 이 표현을 그대로 해결하는 구조로 만든다.

### 2단계: 사전 채점

같은 제안을 세 가지 제목으로 만들어 기존 고객 10명에게 보낸다.

- 고장·영업중단 예방형
- A/S 누락 방지형
- 정기점검 비용 절감형

응답률, 상담 전환, 유료 전환을 비교해 가장 강한 결과 문구만 남긴다.

### 3단계: 반복 가능한 판매자료로 고정

- 1페이지 소개서
- 3분 데모 순서
- 카카오톡 첫 제안문
- 가격·범위·제외사항 표
- 도입 전후 사례
- 고객 등록 체크리스트

세 고객에게 반복 사용한 뒤 별도 마케팅 워크플로로 고정한다.

## 12. 첫 판매 문구

### 제목

> 세차장 장비 A/S, 접수부터 다음 점검까지 놓치지 않게 관리해드립니다.

### 카카오톡 제안 초안

> 사장님, 장비 A/S 요청과 수리 이력이 전화나 카톡에 흩어지면 접수 확인과 이전 수리내용 확인이 번거로워집니다. 대한이엔지에서 설치 장비, 보증기간, A/S 진행상태, 다음 점검일을 한곳에서 관리해드리는 90일 안심관리 시범서비스를 시작합니다. 장비 등록부터 직접 해드리고, 사장님은 링크에서 접수 상태만 확인하시면 됩니다. 첫 3개 사업장만 9만 9천 원에 진행합니다.

### 3분 데모

1. 사업장에 설치된 장비와 보증기간을 보여준다.
2. 휴대전화에서 A/S를 접수한다.
3. 운영자 화면에서 방문일을 배정한다.
4. 고객 링크에 방문 예정일이 표시되는 것을 보여준다.
5. 완료 후 수리·부품 이력과 다음 점검일을 보여준다.

계약 화면이나 기술 구조를 먼저 설명하지 않는다.

- 데모·상담 3곳 이상
- 유료 고객(13.1 파일럿 포함) 2곳 이상
- 실제 A/S 10건 이상 시스템 처리
- A/S 상태 확인을 위한 반복 문의 감소 사례 1건 이상

### 제품화 진행 기준

- 유료 고객 3곳이 같은 핵심 흐름을 사용
- 고객별 맞춤 코드 없이 설정만으로 도입 가능
- 관리계약 갱신 또는 유료 현장점검 발생

### 중단·수정 기준

- 13.2 게이트를 두 번의 사이클(총 8명 이상 접촉) 안에 통과하지 못하면 제안 대상과 문제 정의를 다시 세운다.
- 10곳 모두 9만 9천 원도 지불하지 않으면 기능 개발을 멈추고 제안 대상과 결과를 다시 정의한다.
- 고객이 시스템보다 출장·부품 할인만 원하면 소프트웨어 상품이 아니라 유지보수 멤버십으로 더 좁힌다.
- 내부 담당자가 매일 쓰지 않으면 고객 기능을 늘리지 말고 입력 절차부터 줄인다.

## 15. 주요 위험

- `관리`가 무상 A/S나 무제한 출장을 의미한다고 오해할 수 있다.
- 보증 범위, 출장비, 부품비, 응답시간을 계약서에 명확히 표시해야 한다.
- 고객이 입력하지 않아도 운영 가능한 구조여야 한다.
- 현장 담당자의 모바일 입력이 길면 데이터가 즉시 누락된다.
- 고객 연락처, 주소, 장비 이력, 공유 링크를 개인정보·영업정보로 보호해야 한다.
- AI 자동판단은 오진·보증 분쟁을 만들 수 있으므로 초기에는 요약 보조에도 넣지 않는다.

## 16. MVP 완료 정의

다음 시나리오가 실제 고객 한 곳에서 끝까지 동작하면 MVP가 완료된 것이다.

> 대한이엔지가 기존 고객과 설치 장비를 등록하고, 고객이 모바일 링크로 A/S를 접수하며, 담당자가 방문일을 배정하고, 현장에서 조치와 부품을 기록하고, 고객이 완료 상태와 다음 점검일을 확인하고, 90일 관리비를 실제로 지불한다.

코드 완성이나 화면 개수는 MVP 완료 기준이 아니다.
