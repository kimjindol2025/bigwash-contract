## 1. 🔴 치명적 — 경로 분열

FreeLang v11 `bootstrap.js`의 `load` 구현(`case "load"`, 약 15268행)을 직접
읽어 확인한 동작:

```js
const currentFile = interp.currentFilePath;
const baseDir = currentFile && !path.isAbsolute(filePath)
  ? path.dirname(currentFile) : process.cwd();
```

`load`는 **호출한 파일이 아니라 `interp.currentFilePath` 기준**으로 상대경로를
resolve한다. 그런데 `load` 처리 블록 안에서는 로드되는 파일을 평가하는 동안
`interp.currentFilePath`를 갱신하지 않는다 — 즉 A가 B를 `load`하고 B가 다시
C를 `load`해도, C의 상대경로는 B 기준이 아니라 **최초 진입점(entry) 파일 기준**
으로 풀린다. (`feedback_fl_fx_runtime_traps` 메모의 "load=엔트리기준" 함정과
동일 — 이 저장소에서 실제로 재현됨.)

반면 `file_read`/`file-read`는 `_fl_file_read(p) { fs.readFileSync(p) }`로
구현되어 있어 entry 기준이 아니라 **Node 프로세스의 cwd 기준**으로 resolve된다
(비절대경로일 때). 즉 `load`와 `file_read`는 상대경로 기준점이 서로 다르다.

이 저장소는 이 두 규칙을 모르는 상태로 절대경로를 절반만 리팩터링해서 아래처럼
갈라졌다:

### 수정 원칙 (1차 시도 실패 후 정정)

처음에는 "모든 entry가 `src/` 안에 있으니 `load` 대상도 bare 파일명(`"db.fl"`
등)만 쓰면 entry 기준으로 항상 올바르게 풀린다"고 판단해 그렇게 고쳤다. 하지만
`tests/*.fl`도 `src/*.fl`을 `load`하는 별도 entry라는 점을 놓쳤다 — 예를 들어
`tests/test_sales_flow.fl`(entry, `tests/` 소속)가 `src/washcare.fl`을 로드하면
`interp.currentFilePath`는 계속 `test_sales_flow.fl`로 고정되고, `washcare.fl`
내부의 `(load "phase1-db.fl")`(bare)조차 `tests/` 기준으로 풀려
`tests/phase1-db.fl`(존재하지 않음)을 찾다가 실패했다 — **직접 재현·확인됨.**

즉 이 저장소는 `src/` 안에서만 도는 entry(`server.fl`, `washcare-api.fl`,
`review-server.fl`)와 `tests/` 안에서 `src/`를 불러오는 entry(`test_*.fl`)가
공존해서, "entry와 같은 디렉토리"라는 전제 자체가 성립하지 않는다. `load`가
entry 기준 고정이라는 규칙을 무력화하는 유일한 방법은 **절대경로**뿐이다
(`path.isAbsolute(filePath)`면 baseDir 계산 자체를 건너뜀). 최종적으로
`load`/`file_read`를 포함한 모든 파일 참조를 **entry 위치와 무관하게 항상
실제 저장소 절대경로(`/root/kim/bigwash-contract/...`)로 통일**했다 —
`src/*.fl` 상호간, `tests/*.fl` → `src/*.fl` 전부 동일 규칙.

(`import`는 예외 — `evalImportFromFile`이 로드되는 파일마다 새 서브인터프리터를
만들고 `subInterp.currentFilePath`를 그 파일 자신으로 설정하므로, import된
파일 내부의 `load`는 정상적으로 "그 파일 기준"으로 풀린다. `src/api.fl`의
`import`문은 그래서 상대경로 `"./contract.fl"` 그대로 둬도 안전하다 — 직접
실행해 확인함.)

`db.fl` 기본 DB 경로도 동일하게 실제 저장소 절대경로로 고정한다
(`BIGWASH_DB_PATH` env override는 유지).

## 4. 🔴 수정 과정에서 새로 발견 — `& children` 가변 인자가 동작하지 않음

경로를 고치고 `server.fl`을 처음으로 실제 기동해보니(이전에는 로드 자체가
실패해서 한 번도 끝까지 실행된 적이 없었다), 대시보드가 200은 반환하지만
`<div class="stat-card"></div>`처럼 내용이 전부 비어 있었다. 원인을 직접
재현해 확인:

```
(defn f [a & rest] rest)
(f 1 "x" "y")        ;; => "y"  (배열이 아니라 마지막 값 하나)
(f 1 "x")             ;; => 오류: expects 3 args (a, &, rest), got 2
```

`docs/AI_REFERENCE.md`는 "Rest args: `(defn f [& args] ...)` — args는 배열"
이라고 설명하지만, 이 저장소가 쓰는 FreeLang v11.5.1 런타임의 실제 동작은
다르다 — `&`는 특수 마커가 아니라 그냥 이름 있는 고정 파라미터로 소비되고,
선언된 파라미터 개수를 넘는 인자는 조용히 버려진다. `ui.fl`의 `div`/`header`/
`nav`/`form`/`table`/`thead`/`tbody`/`tr`가 전부 `[attrs & children]` 패턴을
썼고, 그 결과 `(join children "")`가 스칼라 값 하나(또는 버려진 값)에
`join`을 호출해 조용히 빈 문자열을 반환했다 — 에러 없이 UI 전체가 비어
렌더링되는 구조적 결함이었다. 이 코드가 실제로 브라우저에서 열린 적이 있는지
의심스럽다(load 경로 버그 때문에 서버가 뜬 적도 없었을 가능성이 높음).

**수정**: `children`을 가변 인자 대신 명시적 배열 파라미터로 바꾸고, 호출부
(`stat-card`, `contract-row`, `form-group` — 이 세 곳이 전부였다)에서
`[...]` 배열 리터럴로 넘기도록 변경. 수정 후 `/`(대시보드), `/contract/new`
라우트를 직접 HTTP로 열어 계약행 3건·통계카드 4개·폼 라벨이 실제로 렌더되는
것까지 확인했다.

## 6. 새로 발견된 FreeLang 함정 — if 비-tail 분기의 bare 호출이 미평가 thunk로 샌다 (2026-07-21)

`record-call-event`(통화·문자 webhook 기록) 개발 중 직접 재현·확인한 별개의
심각한 런타임 함정. 앞서 4장의 `& children` 가변인자 함정과는 다른 버그다.

**증상**: `defn` 함수(또는 `let` 바인딩) 안에서 `(if cond branch-a branch-b)`가
그 `let`/`do`/함수 몸통의 **마지막(tail) 표현식이 아니고**, 어느 한 분기가
**감싸이지 않은 단일 호출식**(bare call — 예: `(db_exec ...)`, `(careplan-today)`)
이면:
- 분기가 부작용 함수(`db_exec` 등)면 그 부작용이 **조용히 스킵**된다 —
  함수는 정상처럼 반환값을 내지만 DB엔 아무것도 안 쓰인다.
- 분기가 값 생성 함수면 실제 값 대신 **미평가 thunk 객체**
  (`{"fn":"함수명","args":[...]}`)가 그대로 새어나와, 나중에 문자열
  연결·SQL 파라미터 등에 섞여 들어가 엉뚱한 값이나 런타임 에러가 된다.

**재현된 실제 사례 2건**:
1. `src/washcare.fl` `record-call-event` — `(if (nil? occurred-at-ms) (db_exec A) (db_exec B))` 뒤에
   별도로 `{:matched ...}` 반환 맵이 있어서 non-tail이 됨 → INSERT가 항상 스킵됨.
2. `src/washcare.fl` `create-care-plan`(다른 작업자 작성분) — `let`의
   `resolved-starts-at (if (blank? starts-at) (careplan-today) starts-at)`을
   뒤이은 바인딩(`ends-at`)이 참조 → `starts_at` 생략(문서가 명시한 정상
   사용법)시 매번 깨짐. 이 파일의 기존 테스트는 전부 `starts_at`을 명시로
   넘겨서 이 경로를 한 번도 안 거쳤었다.

**수정 패턴**: 문제되는 분기를 `(do (bare-call) 반환값)` 형태로 감싸서
bare 호출이 아니게 만들고, `if` 자체가 진짜로 함수/블록의 마지막 표현식이
되게 한다. `cond`, 중첩 표현식(`(get (호출) :key)`), `do`로 이미 감싼 분기는
이 함정에 안 걸림을 실측으로 확인(하위 에이전트가 `phase1-create-schema`,
`update-ticket-status`, `renew-care-plan` 등 기존 코드 전수 재검증 — 다른
곳엔 없음, 이 2건이 전부).

**교훈**: 값을 반환하거나 부작용을 내는 `if`는 습관적으로 각 분기를 `do`로
감싸서 명시적으로 만드는 편이 이 함정을 원천적으로 피한다. 회귀 테스트:
`tests/test_call_events.fl`(record-call-event), `tests/test_careplan.fl`
10절(create-care-plan, starts_at 생략 케이스).
