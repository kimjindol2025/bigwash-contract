# 대한이엔지 통합관리시스템 — 최상위 메뉴

작성일: 2026-07-19

> 이 문서는 회사 전체 관리시스템의 **최상위 14개 메뉴**를 고정한다. `고객관리`
> (2번) 하위 상세는 이 문서에서 다시 정의하지 않고 `05-customer-management-design.md`
> (필드·데이터모델)와 `06-customer-management-page-tree.md`(화면 구조)를 그대로
> 따른다 — 이 문서는 그 두 문서의 상위 컨테이너다. 나머지 13개 모듈의 하위 페이지는
> 아직 이 문서 수준(대분류)까지만 확정됐고, 각 모듈의 상세 설계는 추후 `05`/`06`과
> 같은 방식으로 모듈별 문서를 따로 만든다.

## 0. 전체 메뉴

```text
대한이엔지 통합관리시스템
│
├─ 1. 홈
├─ 2. 고객관리        (→ 05, 06번 문서)
├─ 3. 상담·문의
├─ 4. 상품·판매
├─ 5. 견적관리
├─ 6. 계약관리
├─ 7. 출장서비스
├─ 8. 연간관리
├─ 9. 회계·수금
├─ 10. 메시지
├─ 11. 일정·할 일
├─ 12. 사진·문서
├─ 13. 통계·보고서
└─ 14. 설정
```

**주의 — 3번 "상담·문의"와 2번 고객관리 하위의 "상담관리"(`06번` 문서 1.5절)는
같은 개념이 두 자리에 나타난 것이다.** `06번` 문서는 상담을 고객관리 모듈
내부 메뉴로 뒀는데, 이 문서는 최상위 독립 모듈로 뒀다. 실제 화면에서는
하나만 남겨야 한다 — 아래 "실제 좌측 메뉴 권장안"(6장)에서는 상담을 고객
그룹 하위(`고객 > 상담·문의`)로 정리해 이 중복을 해소했다. 상담 데이터 모델
자체(`consultations` 테이블 등)는 어느 쪽에 두든 동일하므로 `05번` 문서를
그대로 따른다 — 메뉴 위치만 6장 기준으로 통일한다.

## 1. 홈

```text
홈
├─ 오늘의 업무
├─ 신규 문의
├─ 오늘 출장
├─ 견적 대기
├─ 계약 진행
├─ 입금 예정
├─ 미수금
├─ 사후관리
├─ 연간관리 만료
├─ 최근 고객 활동
└─ 매출 요약
```

> 홈의 역할은 통계 전시가 아니라 "오늘 내가 무엇부터 해야 하는가?"에 답하는 것.

각 카드는 해당 모듈의 대시보드 쿼리를 재사용한다(홈에서 새로 만들지 않음) —
예: "미수금"은 9번 회계·수금의 미수금 목록과 같은 쿼리, "사후관리"는 8·2번의
사후관리 예정과 같은 쿼리. 홈은 모듈별 요약을 한곳에 모으는 조회 계층이다
(`06번` 문서 4장에서 고객 대시보드에 적용한 것과 같은 원칙 — 별도 저장 없이
기존 데이터 조회로 구성).

## 2. 고객관리

이 문서에서는 최상위 목록만 고정한다.

```text
고객관리
├─ 전체/신규/잠재/거래/서비스/연간관리/휴면 고객
├─ 고객 현장
├─ 고객 장비
├─ 중복 고객
└─ 고객 분류
```

하위 페이지 구조, 고객 상세 탭 구성, 데이터 모델은 **`05번`·`06번` 문서가
정본**이다 — 이 문서에서 다시 쓰지 않는다.

## 3. 상담·문의

```text
상담·문의
├─ 전체 상담 / 신규 상담 / 미처리 상담 / 재연락 예정
├─ 견적 필요 / 출장 필요 / 상품 문의 / 불만·민원
├─ 상담 완료
└─ 상담 유형 설정
```

전환 흐름: `상담 → [상품 판매 | 견적 작성 | 출장 접수 | 계약 검토 | 다시 연락 | 상담 완료]`

`06번` 문서 1.5절의 "상담관리"와 데이터 모델·전환 흐름이 동일하다 — 화면
위치를 고객 그룹 하위로 둘지 독립 모듈로 둘지는 6장에서 정리했듯 **고객
그룹 하위**로 통일한다. 이 절은 그 전환 흐름 자체(어떤 상담 결과가 어떤
모듈로 이어지는지)의 정본으로 남긴다.

## 4. 상품·판매

```text
상품·판매
├─ 상품 목록 / 상품 등록 / 상품 분류 / 재고 현황
├─ 주문 접수 / 판매 목록 / 결제 대기 / 배송 관리 / 설치 판매
├─ 취소·반품
├─ 판매 고객
└─ 판매 설정
```

상품 유형: 완제품 장비 / 부품 / 소모품 / 설치 상품 / 수리 상품 / 출장 상품 / 기타 서비스.

`05번` 문서 7장(상품 판매 이력)·24.2절이 이미 지적한 대로, 기존 WashCare의
`part_sales`는 "부품"에 한정된 범위라 이 모듈 전체(완제품 장비 판매, 재고,
배송)를 담기엔 좁다 — 이 모듈의 상세 설계 시 `part_sales`를 확장할지 별도
테이블을 둘지 다시 결정해야 한다(기존 갭으로 이미 기록됨, 재논의 필요).

## 5. 견적관리

```text
견적관리
├─ 전체/신규/작성중/고객발송/검토중/수정요청 견적
├─ 승인 견적 / 계약 전환 / 보류 / 거절 / 만료
└─ 견적 양식
```

견적 항목: 고객·현장·상품·공사·설치비·출장비·운송비·인건비·할인·부가세·특이사항·유효기간.

`05번` 문서 8장·24.3절의 신규 `quotes` 테이블 설계와 그대로 대응한다 — 이
모듈이 바로 그 테이블을 쓰는 화면이다.

## 6. 계약관리

```text
계약관리
├─ 전체/신규 계약 / 계약 검토 / 서명 대기 / 계약 완료
├─ 계약금 대기 / 작업 예정·진행 / 완료 대기 / 잔금 대기
├─ 종료 / 취소 계약
└─ 계약서 양식
```

계약 연결: 고객·승인견적·계약금·중도금·잔금·작업일정·작업범위·출장설치·사진·계약서·보증기간·사후관리.

기존 `contracts` 테이블(`DESIGN.md`) 재사용. `05번` 문서 9장이 이미 지적한 대로
계약금/중도금/잔금, 작업 진행 상태는 `contracts.status` 자체를 세분화하지 않고
9번 회계·수금 및 7번 출장서비스의 상태를 조합한 파생 뷰로 보여준다 — 이
모듈에서 상태값을 새로 늘리지 않는다.

✅ **API·Admin 모듈은 이미 구현됨(7주차, 2026-07-22).** Care
`/care/contracts*` 5종(목록 필터·생성·상세·수정·상태전이)이 `DESIGN.md`의
5상태+items+history를 그대로 노출하고, 이 절이 정한 가드(상태값 비팽창,
`contracts.status`에 계약금/중도금/잔금·작업 진행 흡수 금지)를 지켰다 —
저장 status는 5값 그대로이며 05§17의 세분화 라벨은 Admin UI 표시 맵으로만
존재한다. DELETE 엔드포인트는 없다(취소는 `CANCELLED` 상태전이). 결제·
미수금·PG 연동은 여전히 9번 회계·수금 모듈(미구현) 몫이다. 상세는
`docs/13-contract-management-report.md`, API는 `docs/04-washcare-api.md`
참조.

## 7. 출장서비스

```text
출장서비스
├─ 출장 대시보드 / 신규 접수 / 배정대기 / 일정확정
├─ 오늘 출장 / 이동중 / 작업중 / 부품필요 / 재방문필요
├─ 완료대기 / 출장완료 / 취소
└─ 사후관리 예정
```

출장 상세: 고객·현장·장비·고장증상·전화상담내용·방문일정·준비부품·작업내용·
사용부품·작업전후사진·출장비수리비·결제상태·고객확인·재방문여부·사후관리.

✅ **핵심은 이미 구현됨.** `service_tickets`/`service_visits`(`05번` 문서 10장)가
`RECEIVED→SCHEDULED→IN_PROGRESS→COMPLETED/CANCELLED` 상태 흐름을 이미 갖고
있다. 이 절의 "배정대기/일정확정/이동중/작업중/부품필요/재방문필요/완료대기"는
기존 5단계보다 세분화된 상태 표현인데, `05번` 문서 9.2절이 계약 상태에 적용한
것과 같은 원칙(상태값을 무한정 늘리지 않고 조합 뷰로 표현)을 여기도 적용할지,
아니면 실제로 현장 기사가 "이동중"과 "작업중"을 구분해 입력해야 하는지는
운영 데이터로 확인 후 결정 — 이 문서에서 미리 정하지 않는다.

## 8. 연간관리

```text
연간관리
├─ 관리 플랜 / 가입 고객 / 신규 계약 / 이용 중
├─ 정기점검 예정 / 출장 사용 내역 / 판매 혜택 내역
├─ 남은 서비스 / 만료 예정 / 갱신 대상 / 종료 계약
└─ 수익성 분석
```

플랜 유형: 기본형 / 출장 포함형 / 정기점검형 / 수리 할인형 / 종합관리형 / 고객 맞춤형.

`05번` 문서 11장·`02번` 문서 4장 Phase 2의 `CarePlan` 설계와 그대로 대응
(신규 설계 아님).

## 9. 회계·수금

```text
회계·수금
├─ 회계 대시보드 / 매출 / 매입 / 입금 / 출금
├─ 미수금 / 미지급금
├─ 견적·계약 수금 / 출장 매출 / 상품 매출 / 연간관리 매출
├─ 경비 / 계좌·현금 / 세금계산서 상태
└─ 월별 마감
```

**같은 금액을 반복 입력하지 않는다** — 각 모듈 완료 이벤트가 매출/미수금을
자동 생성한다:

```text
상품 판매 완료 → 매출 생성 → 결제 또는 미수금 생성
출장 완료       → 출장 매출 생성 → 결제 또는 미수금 생성
계약 완료       → 계약금·중도금·잔금 일정 생성
```

`05번` 문서 12장·`02번` 문서 4장 Phase 3의 `PaymentOrder`/`PaymentEvent` 설계와
대응하되, `05번` 문서가 이미 남긴 갭(발생원별 개별 기록 vs `source_type`+
`source_id`로 일반화한 단일 원장)을 이 모듈 상세 설계 시 확정해야 한다.
"매입/미지급금/경비/계좌현금/세금계산서/월별마감"은 `01번` 문서가 1차 MVP에서
제외한 "범용 재고·회계 시스템"에 가까워지는 지점이다 — 이 모듈을 상세 설계할
때 어디까지가 "우리 매출·미수금 확인"이고 어디부터가 "범용 회계 프로그램
대체"인지 경계를 다시 그어야 한다(지금 미리 긋지 않음, 주의만 표시).

## 10. 메시지

```text
메시지
├─ 메시지 작성 / 문자 발송 / 카카오 발송 / 이메일 발송
├─ 발송 예정 / 자동 발송 / 발송 완료 / 발송 실패
├─ 고객 답변 / 발송 이력
├─ 메시지 템플릿
└─ 수신거부 관리
```

자동 메시지 대상: 견적발송·방문일정·기사출발·작업완료·입금요청·미수금안내·
사후관리·보증종료·정기점검·연간관리갱신.

`05번` 문서 13장의 `notification_deliveries` 설계와 대응. 같은 문서가 이미
그은 경계를 유지한다 — **발송 "기록"만 이 시스템이 갖고, 실제 SMS/카카오
게이트웨이 연동·자동 발송 엔진·수신거부 처리 로직은 `01번` 문서 6장 MVP
제외 원칙에 따라 범위 밖**이다. "자동 발송"/"수신거부 관리" 항목은 이후
게이트웨이 연동이 실제로 필요해지는 시점에 다시 범위를 연다.

## 11. 일정·할 일

```text
일정·할 일
├─ 오늘 / 내일 / 이번 주 / 캘린더
├─ 상담후속 / 견적후속 / 계약일정 / 출장일정 / 입금확인
├─ 사후관리 / 연간관리일정
└─ 지연 업무 / 완료 업무
```

> 혼자 운영할 때 빠뜨리지 않기 위한 실행 메뉴.

각 업무 모듈에서 할 일이 자동 생성되어야 한다 — `05번` 문서 16장의
`todo_items` + 파생 쿼리 조합 원칙(저장이 필요한 수동 메모만 테이블, 나머지는
전부 각 모듈 상태 조회로 계산)을 이 메뉴 전체로 확장 적용한다. 이 메뉴가
바로 그 "여러 모듈의 할일을 한곳에 모으는" 화면이다 — 홈(1번)의 "오늘의 업무"
카드와 겹치는데, 홈은 요약(카드 개수·상위 몇 건)만, 이 메뉴는 전체 목록·완료
처리까지 다루는 차이로 구분한다.

## 12. 사진·문서

```text
사진·문서
├─ 전체/고객/현장/장비/출장 사진
├─ 작업 전·후 사진
├─ 견적서/계약서/거래명세서/사업자등록증/세금계산서
├─ 장비 매뉴얼/도면
└─ 기타 문서
```

사진 연결 기준: 고객·현장·장비·출장·계약·작성일.

`05번` 문서 14장의 `attachments`(다형 연결) 설계와 그대로 대응.

## 13. 통계·보고서

```text
통계·보고서
├─ 일간/주간/월간/연간 보고
├─ 고객현황 / 상담전환율 / 견적승인율 / 계약현황 / 출장현황
├─ 상품매출 / 서비스매출 / 연간관리현황
├─ 미수금현황 / 고객별매출 / 지역별현황
```

초기 필수 보고서만 우선: 이번 달 매출 / 미수금 / 견적 대기 / 출장 완료 /
고객별 거래 / 연간관리 만료. 나머지는 각 모듈이 실제로 쌓이기 전까지 만들지
않는다(`01번` 문서 6장의 단계적 확장 원칙과 동일).

## 14. 설정

```text
설정
├─ 회사 정보 / 사용자 정보
├─ 고객 분류 / 상품 분류 / 견적 양식 / 계약 양식
├─ 출장 유형 / 연간관리 플랜 / 회계 항목 / 결제 방법
├─ 메시지 템플릿 / 자동 알림 규칙 / 번호 생성 규칙
├─ 파일 저장 설정 / 데이터 백업
└─ 변경 이력
```

`05번` 문서 13장(고객관리 설정)이 이미 다룬 고객 관련 설정 항목은 여기서
중복 정의하지 않고 참조만 한다.

## 15. 실제 좌측 메뉴 권장안

```text

```

14개 최상위 모듈을 그대로 나열하지 않고 6개 그룹(고객/영업/서비스/관리/분석/
시스템)으로 묶는다. "상담·문의"는 위 0장 주의사항대로 고객 그룹 하위에 둬
`06번` 문서의 고객관리 내부 상담관리와 하나로 합친다.

## 16. 전체 업무 흐름

```text
고객 문의
   ↓
고객 등록 또는 기존 고객 검색     (2. 고객관리)
   ↓
상담 기록                        (3. 상담·문의)
   ↓
상품 판매 / 견적 / 출장 접수      (4·5·7)
   ↓
계약 또는 현장 작업               (6·7)
   ↓
결제·미수금                      (9. 회계·수금)
   ↓
사진·문서 저장                   (12. 사진·문서)
   ↓
사후관리                         (2·8)
   ↓
연간관리 또는 재구매              (8. 연간관리)
```

이 흐름은 `05번` 문서 9장(핵심 업무 흐름), 23장(핵심 자동화)이 고객관리
관점에서 이미 그린 것과 동일한 순환을 회사 전체 모듈 기준으로 다시 그린 것이다.

## 17. 다음 확정 대상

이 문서로 최상위 14개 모듈과 좌측 메뉴 그룹핑까지 고정됐다. `2. 고객관리`는
이미 `05`·`06`번 문서로 하위 페이지까지 확정된 상태다. 다음으로 하위 페이지를
확정할 모듈은 사용자가 이어서 지정할 순서를 따른다 — 이 문서는 그 순서를
미리 정하지 않는다.
