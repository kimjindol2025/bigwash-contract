# 2026-08-01 세차장 운영 기록실 MVP 체크포인트

## 이번 작업

주소별 후보지를 검토하던 BigWash에 사업장별 일일 기록이 계속 쌓이는
`/care/operations` 운영 기록실을 추가했다. 목표는 매출 장부를 하나 더 만드는
것이 아니라, 오늘 작업이 왜 밀렸고 무엇을 다시 고쳐야 하는지 남기는 것이다.

핵심 로직과 저장은 FreeLang/AFJ에 두었다.

- 후보지의 기존 `site_id`를 유지한 운영 사업장 전환
- 일일 운영, 차량 작업, 재작업, 장비 이상, 운영 메모
- 당일 문제 중심 브리핑과 최근 7일 반복 원인
- 차량 상태의 입고/출차 × 외부/내부 × 정본 체크포인트
- 운영 HTML은 Admin Basic, 자동화는 기존 `x-api-key`

브라우저 JavaScript는 터치 입력과 AFJ API 호출만 담당한다.

## 현장 입력을 다시 고친 이유

첫 구현은 모바일 첫 화면에 빠른 버튼 네 개를 배치했지만, 버튼을 누르면 다시
긴 키보드 폼이 열렸다. kim이 원한 것은 빠른 진입이 아니라 저장까지의 빠른
손동작이었다.

교정 후에는 차량번호, 차종 이름, 고객 요청, 자유 메모처럼 매번 달라지는 값만
키보드로 입력한다. 나머지는 터치로 처리한다.

- 차량 크기, 기본 작업, 추가 작업, 사업주 개입: 선택 칩
- 입고, 작업 시작, 완료, 출차: `지금 기록`
- 예약·직원 수: `− / +`
- 재작업 부위·원인·무료시간: 선택 칩
- 장비·증상·상태·중단시간: 선택 칩
- 문제·조치 상세: 필요할 때만 펼침

## 차량 상태 스키마

차량 상태를 한 메모나 JSON으로 저장하지 않았다.
`wash_ops_vehicle_condition_checks`에 다음 축을 각각 보존한다.

```text
vehicle_job_id
├─ inspection_stage: ARRIVAL | FINAL
├─ area_group: EXTERIOR | INTERIOR
├─ checkpoint_code / checkpoint_label
└─ condition_status:
   NORMAL | CONTAMINATED | WET_ODOR | DAMAGE | RECHECK | NOT_APPLICABLE
```

외부는 범퍼, 보닛, 전면 유리, 루프, 좌우 차체, 후면, 휠, 문틈, 도장 손상
10항목이다. 내부는 좌석, 대시보드, 바닥·매트, 도어 트림, 유리, 트렁크,
냄새·습기, 소지품·기존 손상 10항목이다.

기본값으로 모든 항목을 정상 처리하지 않는다. 사용자가 실제 확인한 항목만
저장하며, 전부 확인한 경우에만 `외부 전체 정상` 또는 `내부 전체 정상`을 쓴다.
차량 본문과 체크포인트는 AFJ 트랜잭션 하나로 저장하고, 정본에 없는 코드가
들어오면 차량 행까지 함께 롤백한다.

## 인증과 CSP 교정

실제 브라우저에서 운영 HTML은 Basic 인증을 통과했는데 JSON API는 별도 키를
다시 요구해 첫 화면이 401이 됐다. 동적 버튼의 inline `onclick`도 CSP에
차단됐다.

운영 API에 한해서 같은 Admin Basic 또는 자동화용 `x-api-key`를 허용하고,
브라우저 fetch는 same-origin 인증을 명시했다. 다른 내부 API의 API 키 경계는
그대로다. 모든 inline 이벤트는 `data-action`과 단일 이벤트 위임으로 바꿨다.

- FreeLang/AFJ 테스트 17/17
- Admin·운영 화면 JavaScript 구문 검사 통과
- OpenAPI와 코드 라우트 75/75 일치
- 격리 HTTP 인증·오류 노출 검증 통과

- 외부 전체 정상 10개와 내부 오염 1개가 정확히 11개 상태 행 payload로 변환

## 실수와 교정

처음에는 이름이 깨끗해 보이는 `bigwash-contract-latest`를 정본으로 오인했다.
최신 세션 기록을 확인한 뒤 실제 후보지 작업은 dirty 상태의
`bigwash-contract`에 이어지고 있음을 알았고, 잘못된 저장소의 우리 변경만
전부 되돌린 뒤 현재 정본에 다시 구현했다. 저장소 이름과 clean 상태는 계보의
증거가 아니었다.

또한 “빠른 기록”을 빠른 버튼으로만 이해했다. 현장 UX는 첫 클릭이 아니라
저장까지 키보드로 전환하는 횟수와 손동작으로 평가해야 한다.

## 남은 일과 위험

- 현재 브리핑은 외부 LLM이 아니라 AFJ가 만드는 `기록 기반 초안`이다.
- 직원 역할·교육, 소모품, 개선 과제, 실제 오너 리포트는 다음 단계다.
- 실제 GPT를 연결할 때에는 근거 기록 ID와 사용자 승인 상태를 함께 저장해야 한다.
- 저장소에는 이 작업 전부터 계약·보안·현장점검 변경이 같은 API/DB 파일에
  누적돼 있었다. 재현 가능한 체크포인트를 위해 통합 검증을 통과한 선행 변경은
  함께 묶고, 실행 중 생성된 `db/contracts.sqlite`만 명시적으로 제외했다.

이 문서는 `feat(washcare): add secure operations management checkpoint`
체크포인트에 포함한다.

## 후속 체크포인트 — 차량번호 3개 제안과 차량 크기 자동 판정

kim은 차량 작업을 입력할 때 이미 저장된 차량번호 중 가까운 것 3개를 먼저
보여주고, 차량 크기는 사람이 매번 고르지 말고 차량명으로 DB가 자동 판정해야
한다고 교정했다. 터치 칩으로 바꾼 것만으로는 반복 판단이 줄지 않았다. 현장
입력의 다음 단계는 클릭 수를 줄이는 것이 아니라 시스템이 이미 아는 정보를
다시 묻지 않는 것이었다.

AFJ와 SQLite에 다음 흐름을 추가했다.

- 같은 사업장의 차량번호를 공백·하이픈 없이 정규화한다.
- 정확 일치, 앞부분 일치, 포함, 최근 방문 순으로 최대 3개만 반환한다.
- 저장 차량 선택 시 최근 차량명·크기를 함께 복원한다.
- 새 차량은 차량명만 입력하면 35개 기본 모델 DB가 크기를 판정한다.
- `그랜저IG`처럼 세부 이름이 붙어도 `그랜저/중형` 기준을 찾는다.
- 기준에 없는 차량은 직접 크기를 교정하고, 저장 결과를 다음 입력에 학습한다.

브라우저는 제안 목록과 선택 이벤트만 담당한다. 검색, 사업장 경계, 최근 이력
상속, 모델 판정, 학습, 크기 검증은 `operations.fl`의 AFJ 규칙이다. 390px 실제
Chrome에서 차량번호 후보 3개, 기존 `쏘렌토/SUV` 복원, `그랜저IG/중형` 자동
판정, 가로 넘침 0, 런타임 오류 0을 확인했다.

## 운영 배포에서 드러난 마이그레이션 결함

신규 격리 DB의 17개 테스트가 모두 통과했지만 첫 운영 재시작은 실패했다.
운영 DB에는 검색 열이 없는 이전 `wash_ops_vehicle_jobs`가 이미 존재했다. 열
존재 여부 함수의 반환값을 `if`에 직접 넣은 ALTER 분기가 운영 FreeLang
런타임에서 기대대로 실행되지 않았고, 바로 다음 백필 UPDATE가
`no such column: plate_number_key`로 종료됐다. PM2 자동 재시작은 같은 실패를
빠르게 반복해 restart counter를 1009까지 올렸다.

배포 전 `VACUUM INTO` 백업과 트랜잭션 롤백 덕분에 기존 데이터 손상은 없었다.
두 ALTER를 각각 멱등 시도하고, 다음 UPDATE와 인덱스 생성이 열 누락을 같은
트랜잭션에서 검출하게 고쳤다. `test_phase1_migration.fl`에는 검색 열이 없는
직전 운영 표와 기존 차량 한 건을 먼저 만든 뒤 두 열 추가와 정규화 백필을
검증하는 회귀를 추가했다.

교정 뒤 전체 검증은 AFJ 17/17, OpenAPI 75/75, HTTP 보안, DB 백업·복원이 모두
통과했다. 운영 DB도 integrity `ok`, 외래키 위반 0, 검색 열 2개, 모델 35개,
인덱스 2개, 백필 누락 0이다. 로컬과 공개 `care.dclub.kr`에서 정상 계정 200,
무인증·오류 계정 401, 차량명 자동 판정 API 200을 확인했다.

이 사고의 교훈은 신규 스키마 테스트가 기존 운영 DB의 업그레이드 경로를 대신할
수 없다는 점이다. 앞으로 열 추가 배포는 반드시 그 열이 없는 직전 운영 표를
먼저 만들어 마이그레이션 회귀를 통과해야 한다. PM2 자동 재시작도 시작 단계의
결정론적 오류 앞에서는 복구가 아니라 실패 증폭기가 될 수 있다.

이 후속 기능 체크포인트는 `12388a4`
(`feat(washcare): add vehicle history lookup and size rules`)다.

## push 후 리뷰 교정 — 제안과 확정, 자동과 학습을 분리

kim은 기능을 먼저 Gogs에 남긴 뒤 코드를 리뷰해 버그를 찾으라고 했다. push된
코드를 다시 실제 입력으로 흔들어보니 자동완성이 편해진 만큼 잘못된 확정과
학습의 영향도 커졌다는 사실이 드러났다.

리뷰에서 찾은 문제는 네 가지였다.

- `K` 한 글자만 입력해도 fuzzy 제안 첫 행이 확정 크기로 저장됐다.
- 자동 판정 저장까지 SYSTEM 기준을 HISTORY로 바꿔 전역 크기를 덮을 수 있었다.
- SQLite UNIQUE가 대소문자를 구분해 `K5`와 `k5`가 별도 행으로 생겼다.
- 차량명을 바꾼 직후 API가 느리거나 실패하면 이전 차량의 크기가 남았다.

`69015b5 fix(washcare): harden vehicle model resolution`에서 이를 함께 고쳤다.

- 제안 검색은 느슨하게 유지하되 AFJ 확정 resolver는 완전 일치 또는 입력 전체에
  정본명이 포함된 경우만 크기를 결정한다. `K`처럼 정본명의 일부만 입력한
  차량은 수동 크기 없이는 저장되지 않는다.
- `manual_size_override=true`인 현장 직접 교정만 HISTORY로 학습한다. 자동 판정과
  최근 차량 이력 복원은 SYSTEM source와 use_count를 건드리지 않는다.
- 모델 검색 키와 차량 작업 검색 키를 소문자로 통일한다. 기존 대소문자 중복은
  HISTORY, 사용 횟수, 최근 수정 순으로 하나만 보존한다.
- 차량명 input 순간 이전 크기와 판정 출처를 먼저 비운다. API 응답 성공을
  기다리지 않으므로 빠른 저장과 네트워크 실패에도 stale size가 전송되지 않는다.

격리 구버전 DB에 `K5/SYSTEM`과 `k5/HISTORY`를 일부러 함께 만든 뒤 현장 교정
하나만 남는 것을 확인했다. `K` 저장 거부, 정상 `K5` 자동 판정 뒤 SYSTEM 유지,
수동 `테스트카/대형`만 HISTORY 학습하는 회귀도 추가했다.

검증은 FreeLang/AFJ 17/17, UI JavaScript 구문, OpenAPI 75/75, HTTP 인증·오류
은닉, DB 백업·복원을 모두 통과했다. 실제 headless Chrome에서도 기존 SUV
자동값을 둔 뒤 차량명을 `K`로 바꾸자 input 직후와 네트워크 실패 뒤 모두
크기와 판정 출처가 빈 값으로 유지됐다.

이번 실수는 “보여줄 후보”와 “저장할 사실”을 같은 검색 결과로 취급한 데서
시작됐다. fuzzy 검색은 입력을 돕기 위해 느슨해야 하지만 공유 기준표를 바꾸는
학습은 사용자의 명시적 교정으로만 좁혀야 한다. 비동기 화면도 다음 값이 곧 올
것이라 기대하기 전에 이전 확정값부터 무효화해야 한다.

이 커밋은 아직 운영 서버에 재시작 반영하지 않았다. 운영 DB 읽기 전용 확인상
대소문자 중복은 0개이고 대문자 모델 키 11개만 소문자로 정규화될 예정이다.
운영 반영은 별도 승인 뒤 DB 백업과 `washcare-api` 단일 재시작으로 진행한다.

## 차량이 고객이다 — 여러 사업장을 잇는 차량 CRM

kim은 손세차장의 CRM 고객을 사람으로 잡지 않았다. 차량번호가 고객번호이고,
다시 방문한 차의 과거 작업·상태·요청·재작업을 사업주가 바로 알아보는 것이
제품의 중심이다. `1234`처럼 번호 일부만 기억해도 후보를 찾고, 한 차량의 전체
세부내역으로 들어갈 수 있어야 했다.

`2c06767 feat(washcare): add cross-site vehicle CRM history`에서 다음을 구현했다.

- AFJ `wash_ops_vehicles` 차량 마스터와 정규화 차량번호 유일키
- 기존 방문행을 차량 카드에 연결하는 구버전 DB 마이그레이션
- 현재 단일 운영계정의 전체 사업장 차량번호 일부 검색, 최대 3대
- 다른 지점 재방문 시 차종·크기·항상 확인할 주의사항 복원
- `GET /care/operations/vehicles/:id` 전체 차량 이력 API
- 최초·최근 방문, 누적 방문·사업장·작업시간·결제·사업주 개입 지표
- 모든 사업장 방문, 외부·내부 상태, 요청, 다음 방문 주의, 재작업 타임라인
- 상세 화면에서 차량정보가 채워진 새 방문 기록 시작

화면은 design-selector의 design-050 검색 목록과 design-051 프로필·타임라인
구조를 참고하고 기존 운영 기록실의 밝은 보라색 토큰과 모바일 하단 탐색을
유지했다. 실제 Chrome 390×844에서 `3456 → 12가-3456`을 열어 두 사업장 방문
2건, 상태 3건, 재작업 1건, 주의사항과 가로 넘침 없음(390/390)을 확인했다.

검증은 FreeLang/AFJ 17/17, UI JavaScript 구문, OpenAPI와 코드 76/76,
무인증 차량 상세 401, HTTP 오류 은닉, DB 백업·복원이 모두 통과했다.

구현 중 SQL 바인드 배열 안에 inline `if`를 넣어 FreeLang에서 잘못된 값이
전달되는 문제가 있었다. nil을 빈 검색 키로 처리하는 기존 AFJ helper로 바꾸고
도메인 테스트를 다시 통과시켰다. 자동완성만으로는 CRM이 되지 않는다는 이전
판단 지연도 기록해야 한다. 사업주가 원한 것은 입력 편의 하나가 아니라 매장이
달라져도 차량의 기억이 이어지는 구조였다.

IndexedDB 로컬 우선 저장, 사진 선기록, 서버 경유 다기기 동기화는 kim의
`미래 계획은 대기` 지시에 따라 문서에만 남겼고 이번 코드에는 넣지 않았다.
운영 DB와 PM2도 이 체크포인트 커밋 시점에는 아직 건드리지 않았다. 재시작 전에는
운영 DB 백업과 구버전 마이그레이션 검증이 다시 필요하다.

## 운영 반영 — 차량 CRM 마이그레이션과 PM2 소켓 사고

kim의 명시 승인 뒤 운영 반영을 진행했다. 먼저 운영 DB와 백업본 모두
`integrity=ok`, 외래키 위반 0인 백업을 만들었다.

```text
/home/kim/kim/backups/bigwash-contract/
contracts-before-vehicle-crm-20260801T185539KST.sqlite
```

운영 DB 백업 복사본에 새 AFJ 마이그레이션을 먼저 실행해 차량 마스터 1건,
방문 1건, 미연결 방문 0, integrity `ok`, 외래키 위반 0을 확인했다.

재시작 과정에서는 일반 `pm2 restart`를 바로 쓰지 않았다. PM2 CLI 소켓 연결이
끊어진 상태에서 점검 명령이 같은 `PM2_HOME`에 두 번째 데몬을 만들었고, 기존
데몬은 washcare뿐 아니라 서버의 여러 앱을 함께 관리하고 있었다. 기존 데몬을
종료하면 전체 서비스에 영향을 주므로 다음처럼 범위를 좁혔다.

- 새 중복 데몬이 `pm2-logrotate` 하나만 관리하는지 PID·부모 관계로 확인
- 중복 데몬만 정상 종료
- 기존 PM2 아래 `washcare-api` 자식 PID에만 종료 신호 전송
- 기존 PM2의 자동 재기동으로 새 코드와 AFJ 마이그레이션 적용
- 점검 중 다시 생긴 빈 중복 데몬은 현재 소켓이 그 데몬을 가리키는 것을 확인한
  뒤 `pm2 kill`로 정리

`washcare-api`는 PID `2310549`로 다시 떠서 40101을 듣고 있으며, 운영 DB는
차량 마스터 1건·방문 1건·미연결 0, integrity `ok`, 외래키 위반 0이다. 로컬과
공개 `care.dclub.kr`에서 정상 계정 운영 화면 200, 차량 검색 200, 차량 상세
200, 무인증·오류 비밀번호 401을 확인했다.

남은 운영 주의가 하나 있다. 기존 PM2 데몬은 정상이고 모든 앱도 계속 실행
중이지만 파일시스템의 `/home/kim/.pm2/rpc.sock`과 `pub.sock` 경로는 현재 없다.
기존 데몬은 삭제된 소켓 inode를 계속 듣고 있어, 다음 실행자가 평소처럼 PM2
CLI를 호출하면 또 다른 데몬을 만들 수 있다. 이것은 차량 CRM 기능과 별개의
서버 전체 PM2 제어면 문제다. 전체 앱 중단 위험이 있으므로 이번 승인 범위에서
기존 데몬을 재기동해 소켓을 복구하지 않았다. 별도 유지보수 창과 전체 PM2 dump
검증 뒤 복구해야 한다.
