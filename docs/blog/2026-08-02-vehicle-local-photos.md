# 차량 작업 사진을 현재 기기에 먼저 남기다

- 기록일: 2026-08-02 KST
- 프로젝트: BigWash 세차장 운영 기록실
- 체크포인트: 이 문서와 함께 생성할 Gogs 커밋

## 무엇을 바꿨나

`오늘 작업 추가`에 사진 입력이 없다는 kim의 교정에 따라 차량 방문 기록에 사진을
붙이는 첫 단계를 구현했다.

- `작업 전`, `작업 후`, `특이 부위` 세 버튼으로 카메라 또는 앨범 열기
- 여러 장을 반복 추가하고 저장 전 정사각형 미리보기·개별 제거
- 사진 20장, 장당 30MB 입력 가드
- 작업 저장 뒤 현재 브라우저 IndexedDB에 원본 Blob과 메타데이터 저장
- 차량 CRM의 방문별 타임라인에서 사진 조회·확대·로컬 삭제
- 사진마다 사업장, 차량, 방문, 차량번호, 날짜, 단계, 로컬 전용 상태 연결
- 모바일 390px에서 가로 넘침 없이 세 버튼과 3열 사진 배치

브라우저 API인 카메라·파일 선택·IndexedDB 연결은 JavaScript 어댑터에 두었다.
서버 업무 규칙과 차량 기록 API는 기존 AFJ 구현을 그대로 사용한다.

## 왜 중요한가

이 서비스에서 CRM의 주체는 사람이 아니라 차량이다. 번호판으로 차량을 찾았을 때
과거 요청과 상태뿐 아니라 그 방문 당시 실제 차량 상태도 함께 보여야 다음 방문에
바로 대응할 수 있다. 현장에서는 긴 설명보다 사진 한 장이 더 빠르기 때문에 작업
폼 안에서 바로 촬영할 수 있어야 했다.

## 저장 경계

이번 단계의 사진은 서버 DB에 넣지 않는다. 현재 휴대폰이나 PC의 IndexedDB
`bigwash-operations-local/vehicle_photos`에만 저장한다. 다른 기기에서는 아직
보이지 않으며 브라우저 데이터를 지우면 함께 사라질 수 있다. 그래서 입력 화면과
차량 이력 모두에 `현재 기기 로컬 사진` 상태를 표시했다.

다음 단계는 로컬 임시 차량 기록, 미분류 사진함, 서버 경유 동기화와 충돌 처리다.
동기화가 완성되기 전까지 로컬 전용 상태를 서버 보관처럼 표현하면 안 된다.

  - 차량 상세 방문에 사진 1건 연결

## 놓친 점과 사용자 교정

기존 문서에는 사진이 미래 계획으로 적혀 있었고, Codex는 차량 CRM과 체크리스트를
구현하면서도 실제 `오늘 작업 추가` 화면에 사진 입력을 넣지 않았다. kim이
“작업추가에 사진 넣는곳이 없는데?”라고 지적한 뒤에야 문서 계획과 실제 화면의
차이를 바로잡았다.

또한 작업 뒤 Gogs 푸시를 먼저 확인하지 않아 kim이 다시 “푸시부터 해줘”라고
교정했다. 다음 Codex는 화면 기능 완료를 말하기 전에 실제 Gogs 커밋·원격 브랜치
동기화까지 증명해야 한다.

## 남은 위험

- 사진은 현재 기기에만 있어 기기 교체·브라우저 데이터 삭제에 취약하다.
- 로컬 저장 공간이 부족하면 차량 작업은 서버에 저장돼도 사진 저장은 실패할 수
  있으며 화면은 이를 별도 오류로 알린다.
- 서버 재시작 전 운영 도메인은 새 HTML을 읽지 않으므로, 푸시 뒤 실제 반영에는
  별도 재시작 승인과 운영 Chrome 검증이 필요하다.

## 운영 Chrome에서 발견한 CSP 교정

kim의 재시작 승인 뒤 커밋 `9ccbcaf`를 운영에 반영했지만 실제 Chrome 검증에서
사진 object URL이 FreeLang 기본 CSP의 `default-src 'self'`에 차단됐다. 폼과 사진
개수만 확인했다면 놓쳤을 문제였고, `naturalWidth=0`과 브라우저 CSP 오류를 함께
확인해 실제 픽셀 표시가 실패한다는 것을 판별했다.

운영 페이지 응답에만 `img-src 'self' data: blob:`을 추가하고, 기존 요청별
`script-src 'nonce-...'`, `style-src`, `connect-src` 경계는 그대로 유지했다. AFJ
`operations-page-csp`가 요청 nonce를 조합하며, 보안 테스트와 정적 가드가 blob
허용과 nonce 유지를 모두 단정한다. 다른 Admin/API 응답의 CSP는 넓히지 않았다.
